Docker pour les développeurs juniors : ce que j'aurais aimé savoir

Docker m'a fait peur pendant six mois. Voici comment j'ai fini par l'utiliser vraiment — sans devenir devops, juste pour arrêter de casser mon environnement.

La première fois qu'on m'a parlé de Docker, j'ai fait ce que font beaucoup d'étudiants : j'ai ouvert la doc, j'ai vu des mots comme « cgroups », « namespaces », « union filesystem » — et j'ai refermé l'onglet. Six mois plus tard, j'ai croisé Docker dans un projet pro et je n'ai plus pu faire semblant. Voici le récit de ce passage, et les quelques principes qui m'auraient fait gagner du temps.

Pourquoi on en a besoin, concrètement

Le problème que Docker résout, ce n'est pas « déployer dans le cloud ». C'est « ça marche sur ma machine ». Vous installez PostgreSQL 16 chez vous, vous codez contre, vous poussez sur GitHub. Votre collègue tire le code, installe PostgreSQL 14, et rien ne marche. Docker coupe court à ça : vous décrivez votre environnement dans un fichier, et tout le monde obtient la même chose.

Pour un junior, le bénéfice est immédiat. Vous n'installez plus rien sur votre machine hôte. Vous ne corruptionnez plus votre Windows avec cinq versions de Python. Vous lancez un docker compose up, et la base, l'API, le frontend tournent.

Les trois commandes qui changent tout

Je m'étais noyé dans la doc. En réalité, pour démarrer, trois commandes suffisent :

docker build -t mon-app .            # construire l'image
docker run -p 8080:80 mon-app         # lancer un conteneur
docker compose up                     # lancer tout un stack

Avec ça, vous êtes opérationnel. Le reste (volumes, networks, multi-stage builds) vient quand vous en avez besoin — pas avant.

L'erreur classique du débutant

La première image que j'ai écrite faisait 1,4 Go. J'avais pris une image de base Ubuntu complète, j'avais installé Python avec apt, puis mes dépendances, puis mon code. Ça marchait. C'était monstrueux.

La règle : partez d'une image alpine. Pour Python, python:3.12-slim ou python:3.12-alpine. Pour Node, node:20-alpine. Vous passez de 1,4 Go à 120 Mo. Et vous réduisez la surface d'attaque en production, ce que les devs seniors vous reprocheront toujours de ne pas faire.

Le Dockerfile minimal que j'utilise tout le temps

FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "app.py"]

Rien de sorcier. Et c'est exactement ce qu'il faut pour 80% des projets étudiants. Les 20% restants (multi-stage, cache, build args) sont des optimisations, pas des prérequis.

docker compose : le moment déclic

Le déclic, c'est quand j'ai compris que docker compose n'était pas une variante de Docker mais un orchestrateur de plusieurs conteneurs. Vous décrivez, dans un fichier YAML, votre API + votre base + votre frontend, et un seul up lance tout, dans le bon ordre, avec les bonnes variables d'environnement.

services:
  api:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://user:pass@db:5432/app
    depends_on:
      - db
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: pass
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  db-data:

C'est ce fichier qui m'a fait passer de « j'installe des trucs » à « je décris mon système ». Et ça, c'est un vrai changement de mentalité — pas seulement une nouvelle commande.

Le piège caché : les volumes

On ne vous le dit pas tout de suite, mais si vous ne mettez pas de volume sur votre base, vous perdez toutes vos données à chaque down. J'ai appris ça en perdant trois jours de données de test. Depuis, la ligne volumes: - db-data:/var/lib/postgresql/data est la première que j'ajoute. Toujours.

Bref

Docker n'est pas un sujet de devops. C'est un outil de propreté. Pour un junior, l'apprendre tôt, c'est arrêter de pourrir sa machine et commencer à livrer un environnement reproductible. Les concepts avancés viendront. Commencez par les trois commandes, et vous en saurez déjà plus que la moyenne des L2.
